## Summary

- Adds a self-contained claim library to the executor: an HTTP client for git-rest's leased claim-ref endpoints (git-rest spec 018) plus a lease manager that claims, renews, fences, takes over, releases and re-adopts claims, so that later a task runs on exactly one cluster.
- A claim is a ref on the shared vault origin with a 5-minute lease, renewed every 60 s by compare-and-swap. Losing the swap means the claim is lost and the task's Job is deleted. A holder that cannot renew stops its own Job no later than 60 s before its lease ends, and nobody else may take the claim until 30 s after the lease ends.
- Taking over an expired claim is a single compare-and-swap write against the expired claim's sha, so of two executors racing for it exactly one wins.
- A restarted executor re-adopts the claims whose Job still runs, releases the rest, and fences the ones whose lease is too close to its end.
- Library, unit tests and a protocol doc only, all tested on a fake clock against an in-process fake git-rest (the real endpoint is not deployed). Nothing in the live dispatch path calls it yet.

## Problem

Agent tasks are moving from a central cluster assigner to pull-based claims: each cluster's executor claims a task by creating a ref on the shared vault origin through its git-rest instance, renews it while the Job runs, and deletes it when done. git-rest spec 018 adds the server side (list / compare-and-swap create-renew / compare-and-swap delete under `refs/claims/`), but the executor has no client for it and no lease logic. The lease rules are where the correctness lives — who wins a race, when a holder must stop its own Job, when another cluster may take over, what a restarted executor does with claims it held — and they must be pinned by deterministic tests before any of it is wired into dispatch, or a timing bug ships as two clusters running the same task or a task that nobody runs.

## Goal

The executor repository contains a claim library, fully unit-tested on a fake clock against an in-process fake git-rest, that implements the lease protocol below exactly: one winner per create race; a held claim is renewed by compare-and-swap; a lost swap deletes the Job; a holder that cannot renew deletes its Job at or before 60 s before its lease ends; another executor takes over an expired claim no earlier than 30 s after the lease ends, by one compare-and-swap write, and only one taker wins; a finished Job releases its claim; a restarted executor re-adopts, releases or fences each claim it held. `docs/claim-lease-protocol.md` documents the constants, state machine and the fence / takeover / restart rules. The executor's runtime behaviour is unchanged.

Protocol constants (invariants, not configuration): lease length 300 s; tick interval 10 s; renew interval 60 s; fence point `fenceAt` = `lease_until` − 60 s, fence fires when now > `fenceAt` − 10 s; takeover grace 30 s after `lease_until`; per-request timeout cap 30 s.

- No `spec.rerunOnLostClaim` field or lost-claim decision here — that is the separate spec `specs/config-rerun-on-lost-claim.md`. The takeover result reports the previous `task_id` so that decision can be applied later.
- No deploy, no nuke dev rollout, no prod, no sun. No operator verification rung — rollout rungs belong to a later rollout task.
- No new scenario: every behaviour is reachable with an in-process fake server and a fake clock.
- Do NOT add knobs for lease length, tick interval, renew interval, fence margin, takeover grace or request timeout — invariant; if a future consumer demands variation, that is a separate spec.
- Do NOT add retries inside the ref client — a `409` is final and any other failure is reported to the lease manager, which decides from its own clock.

## Assumptions

- The server contract is git-rest spec 018 (`git-rest` repo, `specs/in-progress/018-leased-claim-ref-operations.md`): `GET /api/v1/refs?prefix=<claims/...>` → JSON array of `{ref, sha, cluster, task_id, lease_until}`; `PUT /api/v1/refs/<key>` with body `{expected_sha, cluster, task_id, lease_until}` → `{ref, sha}`; `DELETE /api/v1/refs/<key>?expected_sha=<sha>` → `{ok:true}`. Empty `expected_sha` on `PUT` means "must not exist". `409` = lease mismatch, never retried. git-rest never judges expiry (018 non-goal 1): takeover is the caller passing the expired claim's sha as `expected_sha`. The returned sha differs on every successful `PUT` (server nonce), so a writer recognises its own write by the (`cluster`, `task_id`, `lease_until`) triple, not by the sha (018 AC20).
- A list by prefix matches whole path components and can return refs under the key as well as the key itself (018 DB1). A list entry whose commit vanished between list and fetch is dropped by git-rest.
- The endpoint is not deployed; nothing in this spec talks to a real git-rest.
- Throughout this spec a claim key includes its `claims/` prefix (for example `claims/task/abc123`), so the request path is `/api/v1/refs/<key>` and the listed `ref` is `refs/<key>`.
- A renew that fails and whose read-back shows the ref still at the held sha is one failed interval: the claim is still held and the next renew uses the held sha.
- The gateway auth headers are the existing git-rest contract used by the file client: `X-Gateway-Secret` and `X-Gateway-Initator` (deliberate misspelling), both omitted when the secret is empty.
- Clocks across clusters agree within a few seconds; the fence margin plus takeover grace (90 s between the holder's latest Job stop and the earliest takeover) absorbs that.
- One executor process per cluster name holds claims at a time; two live processes with the same cluster name are outside this protocol (see Failure Modes).
- `docs/claim-lease-protocol.md` (written by this spec) is the reference for the protocol; the later wiring and rollout specs cite it.

## Desired Behavior

1. **Ref client.** A client for the three 018 endpoints lists claims under a prefix, creates/renews a claim by compare-and-swap, and deletes a claim by compare-and-swap. It sends the same gateway headers as the existing file client, bounds each request by the caller's context and a 30 s cap, issues exactly one request per call, maps `409` to the sentinel `ErrLeaseConflict` (matchable with `errors.Is`) and every other non-`200` or unparseable reply to a wrapped error carrying the status. It never logs or returns the gateway secret. A counterfeiter fake is generated for it.
2. **Claim and release.** Claiming a key for a task sends a create with empty `expected_sha` and `lease_until` = now + 300 s; on `200` the manager holds (key, task id, sha, the exact `lease_until` string it wrote). A create answered by any non-`409` failure is read back: the listing shows the triple this create wrote → held at the listed sha (`recovered`); otherwise the claim returns an error and is not held (`error`). Releasing — called when the task's Job has ended — deletes with the held sha; `409` means already released and is not an error; any other failure keeps the claim held and later ticks retry the delete instead of renewing, until the fence point, where the fence path applies (behaviour 4). A manager is constructed with a non-empty cluster name, a ref client, an injected Job control (is a task's Job running / delete a task's Job), a current-time getter and a `WaiterDuration` from `github.com/bborbe/time`; an empty cluster name is rejected at construction. Every read of a single key matches the listing entry whose `ref` equals `refs/` + key exactly; no such entry means absent.
3. **Tick and renew.** An explicit tick method reads time only from the injected clock. At tick start, before any network call, it evaluates the fence for every held claim and retries any pending Job deletion. It then renews, one after another, every held claim whose last renew attempt (or create) is ≥ 60 s old, and every claim restart recovery took on since the previous tick: `expected_sha` = held sha, new `lease_until` = now + 300 s. Every request a tick sends — renew or read-back — has deadline = min(30 s, earliest `fenceAt` among the held claims − now), and after every request the fence is evaluated again for every held claim; a claim fenced at that point is not read back. `200` → adopt the new sha and `lease_until`. `409` → claim lost: delete the task's Job, drop the claim without contacting git-rest, count `claim_lost`, log the key, task id and held sha. Any other failure → read the key back: the ref carries the (cluster, task id, `lease_until`) triple this renew wrote → adopt the listed sha (`recovered`); the ref is still at the held sha → still held (`renew_failed`); the ref is absent or holds any other write → lost, as for `409`; the read-back itself fails → still held (`renew_failed`). A loop wrapper calls the tick, then waits 10 s through the injected `WaiterDuration`, and repeats until its context is done; it starts no raw goroutine.
4. **Fence.** A held claim is fenced when now > `fenceAt` − 10 s (so the deletion lands at or before `fenceAt` with 10 s ticks): the manager deletes the task's Job (skipped when the claim is in release because its Job already ended), then sends one best-effort `DELETE` with the held sha whose `409` or error is ignored, drops the claim and counts `fenced`. A fenced claim is never renewed.
5. **Job deletion failure.** When deleting a task's Job fails on the lost or fence path, the manager counts `error`, keeps the claim held in a pending-deletion state — no renew, no ref `DELETE` — and retries the Job deletion at every tick until it succeeds; then it finishes the path (lost: drop; fence: best-effort ref `DELETE`, drop) without counting the outcome a second time.
6. **Takeover.** To take over a key, the manager reads it. Absent → it claims the key as in behaviour 2 and reports no previous task. Present with now < `lease_until` + 30 s, or with `lease_until` not parseable as RFC3339 → it returns `ErrLeaseNotExpired` without any write (`takeover_too_early`; an unparseable value additionally logs a WARN naming the ref). Otherwise it sends one `PUT` with `expected_sha` = the listed (expired) sha and a fresh lease; `409` → `ErrLeaseConflict`, takeover over, no further request (`conflict`); `200` → the manager holds the claim and returns the previous claim's `task_id` (`taken_over`); any other failure → the same read-back rule as a create (`recovered` and held with the previous `task_id` reported, or `error` and not held).
7. **Restart recovery.** On start the manager lists `claims/`, keeps entries whose `cluster` equals its own, and for each: now > listed `lease_until` − 70 s (the tick fence rule, now > `fenceAt` − 10 s) → fence it (delete the task's Job if it is running, best-effort `DELETE` with the listed sha, no adopt; `fenced`); if that Job deletion fails, the claim enters the DB5 pending-deletion state at the listed sha — no renew, no ref `DELETE` — and the deletion is retried every tick until it succeeds; otherwise Job running → hold it at the listed sha and `lease_until` with no create (`adopted`), and ticks renew it from there; Job not running → `DELETE` with the listed sha (`released`; `409` → `already_released`); the running check fails → count `error`, hold the claim and keep renewing it, and re-ask the running check at every tick until it answers (running → `adopted`; not running → release). Entries of other clusters are never touched. Outside restart recovery, a listed claim whose `cluster` equals the manager's own name but which the manager does not hold is treated exactly like any other holder's claim.
8. **Key derivation, counters, doc.** A pure function maps (task type, task id, owner, repo) to a key: types `update-go`, `release`, `pr-review`, `build-fix` → `claims/repo/<owner>-<repo>` with owner and repo each lowercased; every other type → `claims/task/<task id>`; any component that is empty, contains `/` or `..`, starts with `.`, ends in `.lock`, or contains a character outside `[A-Za-z0-9._-]` is rejected with an error. `executor_claim_total{result}` counts every outcome named in AC9, all 13 series pre-initialised to 0. A mismatch audit compares the held claims against a given set of running Jobs and adds 1 to `executor_claim_mismatch_total` per task with a Job and no held claim and per held claim with no Job, logging which case each was. `docs/claim-lease-protocol.md` describes the constants, the state machine (claimed → held → renewed / recovered / lost / fenced / released, plus pending deletion and release), and the fence, takeover and restart rules exactly as in behaviours 2–7.

## Constraints

- The executor's runtime behaviour is unchanged: nothing outside the claim package and its generated mock imports it (AC11), and all existing tests pass.
- Gateway header names and their omission when the secret is empty match the existing git-rest file client exactly; the secret is never logged.
- Time comes only from the injected `github.com/bborbe/time` current-date-time getter, and the loop's wait only from the injected `github.com/bborbe/time` `WaiterDuration`; tests drive the clock with `SetNow`, use the `WaiterDuration` fake, and never sleep.
- No raw `go func` and no direct `time.Now/Sleep/After/AfterFunc/NewTimer/NewTicker/Since/Until/Tick` in production code of the claim package.
- Lease manager state is safe for concurrent use by the tick loop and claim/release/takeover callers; `go test -race` stays green.
- Keys and task ids never become metric label values. Existing metric names and series are unchanged; the two new counters are additive.
- `## Unreleased` in `CHANGELOG.md` appears exactly once; the release tag is cut manually (`autoRelease: false`).

## Failure Modes

| Trigger | Expected behavior | Recovery (observable) | Reversibility / Concurrency |
|---|---|---|---|
| Two executors create the same key at once | One holds the claim; the other gets `ErrLeaseConflict`, no retry | `conflict` +1 on the loser; the fake/origin ref holds the winner's sha | Single winner by origin CAS (AC1) |
| Two executors take over the same expired claim | Both `PUT` with the expired sha; one `200`, one `409` | `taken_over` +1 on the winner, `conflict` +1 on the loser | Single winner by origin CAS (AC3) |
| Renew answered `409` (another holder replaced the ref) | Job deleted, claim dropped | Job-control deletion recorded; `claim_lost` +1; log names key and held sha | Job deletion irreversible |
| Renew, create or takeover times out after git-rest applied it (partial progress) | Read-back finds own triple → hold at the listed sha | `recovered` +1; next renew `PUT` carries the adopted sha | AC5 |
| Create or takeover fails and was not applied | Not held; error returned | `error` +1; the read-back `GET` recorded; no further write | Nothing to undo |
| git-rest / origin unreachable (external unavailability) | Renews fail; Job deleted at or before `fenceAt` | `renew_failed` per interval, then `fenced` +1 and one best-effort `DELETE`; the next executor's takeover `PUT` at ≥ `lease_until` + 30 s | 90 s gap between Job stop and earliest takeover |
| git-rest hangs (rate limit, slow origin) | Each request's deadline is capped at the earliest `fenceAt` among held claims, so no fence is delayed | Fence deletion recorded at or before `fenceAt` (AC2 b3) | — |
| Job deletion fails (Kubernetes API error) on the lost or fence path | Claim kept in pending deletion: no renew, no ref `DELETE`; deletion retried every tick | `error` +1 per failed attempt; one Job-control deletion call per tick until success; then the best-effort ref `DELETE` (fence) is recorded (AC2 c) | Two Jobs can overlap if deletion keeps failing past `lease_until` + 30 s and another cluster takes over |
| Job running check fails during restart recovery | Claim held and renewed; check re-asked every tick | `error` +1; renew `PUT`s for the claim continue; `adopted` +1 or a release `DELETE` once the check answers (AC4 row E) | No ref is released on an unknown Job state |
| Clock skew between clusters below 90 s | Fence margin + takeover grace keep the old Job stopped before the new one starts | — | Skew ≥ 90 s can overlap two Jobs — outside the protocol's assumption |
| Executor crashes mid-Job and restarts within the lease | Running Job → adopt; finished Job → release; lease within the fence window → fence | `adopted` / `released` / `fenced` +1; no create `PUT` (AC4) | No re-create, no orphan |
| **Known limitation:** executor down longer than `lease_until` + 30 s while its Job keeps running | Nothing renews and nothing fences (the process is gone); another cluster takes over and starts a second Job; the two Jobs overlap until the old Job ends or the old executor returns | On restart the old executor's entry is gone, so it neither adopts nor releases; the mismatch audit counts its running Job as "Job without held claim" (`executor_claim_mismatch_total` +1). Stopping that Job is the later wiring spec's job | Overlap window = downtime beyond the lease |
| **Known limitation:** two live executor processes with the same cluster name (e.g. a rolling update) | The new one adopts the old one's claims while the old one still renews; one of them gets `409` and deletes the shared Job | `claim_lost` +1 on one process. The wiring spec must deploy one process per cluster at a time (Recreate strategy) | Job deletion irreversible |
| Release fails with `500` | Claim stays held; later ticks retry the delete; at the fence point the fence path sends one last best-effort `DELETE` and drops the claim | `error` +1 per failed release; a `DELETE` with the same sha per tick; `fenced` +1 at the fence tick; afterwards no request names the key and the ref expires (AC6) | Ref left to expire and be taken over |
| Listed claim with empty / unparseable `lease_until` (schema drift, foreign writer) | Takeover refused | WARN log naming the ref; `takeover_too_early` +1; operator deletes the ref with its sha | Ref stays until removed |
| Listing entry dropped by git-rest (commit vanished between list and fetch) | The key reads as absent | Renew read-back → `claim_lost` +1; takeover → create `PUT` with empty `expected_sha` | — |
| Job ran with no held claim, or claim held with no Job | Audit adds 1 per case and logs which | `executor_claim_mismatch_total` delta; log names the task id and the case | — |

## Security / Abuse Cases

- **Trust boundary:** the client writes refs on the shared origin through git-rest with the gateway secret; the secret travels only in the `X-Gateway-Secret` header, never in logs, errors, URLs or metric labels.
- **Input shaping:** keys come only from the key-derivation function, which rejects components that would be invalid or traversing; every path segment is percent-escaped; `expected_sha` is only ever empty or a sha the server returned.
- **Untrusted server data:** listed metadata can be written by any git-rest caller. An unparseable `lease_until` never enables a takeover; a sibling ref under a key is never mistaken for the key (exact `ref` match); a foreign `cluster` value is never adopted or released by restart recovery.
- **Hangs / retry storms:** every request has a deadline of at most 30 s and never past the earliest `fenceAt`; the client never retries; the loop stops on context cancellation; a `409` is never retried; Job-deletion and release retries happen at most once per 10 s tick.
- **Metric cardinality:** keys and task ids never become metric label values.

Rationale: prompt 1 fixes the wire contract and builds (and proves) the fake every later test uses; prompt 2 holds all timing logic in one place so the state machine is designed once; prompt 3 is small independent surfaces, the protocol doc written from the finished behaviour, and the final gate. 8 behaviours × 15 ACs exceeds the 50 guideline; the decomposition keeps each prompt to one layer, and the Config field was split out into `specs/config-rerun-on-lost-claim.md`.

## Do-Nothing Option

git-rest's claim endpoints ship with no consumer, and the move from central assignment to claims cannot start: "a task runs on exactly one cluster" and "a powered-off cluster loses no task" stay unsolved, and sun cannot join the pool under claims. Writing the lease logic directly inside the dispatch path instead would mix the timing rules with Kafka and reconcile code, where they cannot be tested on a fake clock — the exact place a fence or takeover off-by-one-tick bug would hide until two clusters run the same task in prod.
