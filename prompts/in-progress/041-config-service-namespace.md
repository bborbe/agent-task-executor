<summary>
- A `spec.type: service` Config can now name the namespace its long-running StatefulSet lives in, instead of being pinned to the executor's own namespace by the reconciler's constructor.
- An unset namespace means "the executor's own namespace", so the two live service agents behave exactly as they do today and the deploy is a no-op.
- A Config that explicitly names the executor's own namespace is refused on the reconcile path itself, not merely by a helper that nobody calls, so no Config can be written to opt out of isolation.
- The executor's own Kubernetes schema declares the new field as strictly as it declares the job one, so an invalid namespace is refused at admission instead of failing later at create time.
- The value survives the resolver, and a Config edit that changes only this field is detected rather than silently ignored.
- Removing a Config's long-running workload now targets that Config's resolved namespace, because a delete aimed at the executor's own namespace leaves the moved workload running while reporting success.
- Changing the namespace on a live Config removes the previous copy, because the reconcile path only ever created and updated.
- No namespace, policy, RBAC, Service or ingress is created here — that stays in the `bborbe/agent` chart.
</summary>

<objective>
Add `ServiceNamespace` to the Config CRD type and to `AgentConfiguration`, declare it in the binary's own CRD schema with the same validation as `jobNamespace`, carry it through `convert()`, add the pure rule `ResolveServiceNamespace` sharing one helper with the job rule, and make `ServiceReconciler` resolve and use it for create, delete and the removal of a previous-namespace copy. End state: a Config's `spec.serviceNamespace` survives the whole path from API object to the StatefulSet's namespace, an unset field leaves every existing object unchanged, and a namespace change leaves exactly one workload running.
</objective>
