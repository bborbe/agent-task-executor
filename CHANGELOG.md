# Changelog

All notable changes to this project will be documented in this file.

## Unreleased

- fix: **a succeeded Job whose phase never moved is parked, not re-driven forever.** v0.46.3 made the re-drive streak count published failures instead of spawns, which correctly stopped charging a successful spawn — but it also removed the only thing that bounded a task whose agent exits 0 without moving the phase. Such a record is a deliberate human park, and the reconcile found it eligible on every pass: an unbounded spawn loop where there used to be a strand. The reconcile now publishes `phase: human_review` for it, which is already in the executor's terminal-phase set, so the record leaves the loop the way any terminal phase does.
  The decision lives in the reconcile, immediately after `recentlySucceeded`, and **that placement is the fix**. The park has to wait out the write-back — a succeeded Job means the agent published its result, but the vault learns about it on the controller's own cycle, so for up to `SuccessGracePeriod` the task file still reads the phase the Job ran for and an in-flight write is invisible. That is exactly the window `recentlySucceeded` suppresses re-drive in, so a park evaluated anywhere slower — the job watcher's informer resync is 5 minutes against the reconcile's 60 seconds — would become possible at the instant the re-drive resumes and lose the race almost every time. Sharing the decision point makes the two mutually exclusive by construction: one pass either suppresses, parks, or spawns.
  The discriminator is **the phase the last Job succeeded for**, not "is the phase still a drive phase". A Job is spawned for one phase and the agent may advance the task inside it and still exit 0 — an agent that finishes `planning` writes `phase: execution` and expects the next phase to be driven. Parking on "still a drive phase" would rewrite `human_review` over that advance and stall every multi-phase agent at its first phase; `recentlySucceeded` compares the same two values for the same reason. The comparison is against the reconcile's own task, never the `TaskStore` entry, whose phase is the spawn phase by construction and would match the record every time.
  **This changes an existing contract:** a task that succeeded at its current phase and is still there past the grace used to be re-driven, on the theory that its write-back had been lost. That case is indistinguishable from a park at this distance, and parking leaves the ambiguity to a human instead of silently re-running the work. **Recovery:** an operator un-parks by moving the task's `phase` back to a drive phase. The park consumes its success record when it fires, so a re-armed task spawns on the next pass rather than being re-parked — without that, the record would outlive its meaning and the recovery path would silently do nothing until the record aged out an hour later. A publish failure is logged and the next pass retries.

## v0.47.0

- feat: **every reconcile-floor refusal is attributable to the gate that made it.** Six of the eight gates in `reconcileTask` returned silently, so a refused record was indistinguishable from one that was never in the candidate set at all. `executor_reconcile_refused_total` is a new counter labelled by a closed `gate` set — `foreign_cluster`, `unresolved_config`, `terminal_status`, `status_not_triggered`, `phase_not_triggered`, `terminal_phase`, `stage_mismatch`, `no_routing` — with all eight series pre-initialised at zero, and each refusal also emits one `event=reconcile_refused` line at V(2) carrying the task's type, phase, status, stage and cluster. The counter moves on every refusal; the log line is emitted only when a task's gate differs from the last one recorded for it, so the per-pass volume stays flat while a gate change — the actionable event — is never lost. The two gates that already logged (`unresolved_config` and `stage_mismatch`) keep their existing lines unchanged, and eligibility itself is untouched: every input that refused before still refuses and every candidate is still a candidate.

## v0.46.3

- fix: **a successful spawn no longer consumes the re-drive budget.** The streak advanced on every successful `SpawnJob` while a reason was recorded only from `PublishFailure`, so a Job that exited 0 published no evidence yet still reached the cap — where the classifier had nothing to read, returned `unknown`, and refused the record forever with no abort and no release. Measured on dev 2026-10-27: 83 `class=unknown` lines across 11 distinct task ids. The streak now counts **published failures** and is written by the result publisher beside the reason, so the count and the evidence it is classified from cannot diverge; `recordRedriveSpawn` keeps only the in-memory floor used when the store is unreadable.

## v0.46.2

- fix: **a foreign `current_job` no longer reads as a finished one when the store is empty.** `jobProvablyFinished` treated `stored == ""` as proof the Job in the shared frontmatter had ended, which is true only for a Job this executor created before a restart. On a cold pod — a restart, or a task this executor never spawned — the frontmatter can just as well name another cluster's Job that is still running, and "not active here" then authorised a second cluster to start it. The concurrent case was measured on 2026-10-22 (`94c1801c` ran on sun and nuke prod for 2 m 33 s) and the guard added for it in v0.36.0 covers only the store-mismatch half, because a cold pod has no entry to compare. The no-store-entry arm now asks the one shared record that can answer: the task's claim, written before a Job is created and released when it ends (held for the success grace after a success). A live claim suppresses the spawn and re-defers it on the existing 30 s path under the existing `skipped_foreign_job` counter; `ErrClaimFree` releases it. A claim past its lease **by the takeover grace** counts as free — not one merely past its lease, because inside that grace the protocol still treats the holder as possibly running; an unreadable lease counts as held, and a failed read suppresses and retries on the next pass rather than failing the message, since a claim store that cannot be read is not evidence that nothing holds the task. Only claim mode `on` probes: `shadow` takes claims but never blocks a dispatch, so a held claim must not suppress a spawn there. Claim mode off keeps no such record, so in both modes the previous behaviour stands and is logged as `event=foreign_job_unprobeable` rather than hidden; that residual is stated, not resolved. The probe reads the same claim key the spawn path would take, from a lazily built typed client, so it costs one read per dispatch pass on a task whose store entry is empty and nothing on any other.

- fix: **`golang.org/x/net` moves to v0.62.0 for two advisories with a fix available.** `govulncheck` flagged `GO-2026-6860` and `GO-2026-6866` (quadratic complexity coalescing text nodes, and an ancestor-namespace check when rendering raw text) against v0.60.0, whose fixed version is v0.62.0, so `make precommit` — and therefore CI — fails on the tree. `golang.org/x/crypto`, `sync`, `sys`, `term`, `text` and `tools` move with it; all are indirect. Bumped rather than added to `VULNCHECK_IGNORE`, because an advisory with a published fix is not a tolerance.

## v0.46.1

- fix: **the divergence check names a divergence before it names an absence.** Both classes shared one 20-line budget and were emitted in id order, so a flood of absent ids spent the budget before any divergence was reached — measured on dev 2026-10-27, 74 absent against 3 divergent, one of the three unnamed. Divergences are the finding the check exists to report, so they are named first and counted separately; the summary now carries `named` and `named_absent` rather than one ambiguous `named`. The counts themselves were never truncated and still are not.

## v0.46.0

- test: **the view/vault divergence check is pinned end to end through `ReconcileOnce` against a real `httptest` index.** `pkg/handler/view_divergence_test.go` drives the real `claim.NewVaultAPIIndexClient` so the auth and envelope paths are exercised: a status-only and a phase-only divergence each emit one `event=view_divergence` line with both sides of both fields and a summary carrying `compared=3 divergent=1 index_age_seconds=12 warnings=` from the index, agreement emits neither, an owned id missing from the index reads `event=view_divergence_absent` and moves only the `absent` series, and an empty index reports all three owned ids absent (`compared=0`). The negative cases are at the same level: a closed port logs `event=view_divergence_read_error`, moves the `read_error` series and still drives and spawns its candidate; a handler built without `WithVaultAPIIndexClient` emits no line and moves no series; and a not-ready view, unstamped or mismatched vault, or already-expired context makes zero index requests. A 50-task pass makes exactly one request, and the request is pinned as an unfiltered, authenticated `GET /api/v1/tasks` with the gateway header pair. Per-id lines are capped at 20 a pass and the summary carries `absent` and `named` alongside `divergent`: an index that returns nothing classifies every owned task as absent, and naming all 7,232 of them once a minute would be a worse fault than the divergence it reports. The counts are never truncated — only the named lines are.

- feat: **the reconcile pass reports every owned task whose view state diverges from vault-api's index.** After sorting candidates and before driving them, a pass that still has budget reads the index once and joins each owned view task's `task_identifier` to `items[].id`, comparing both `status` and `phase`; a difference in either is a divergence and the finding carries both sides of both fields. An owned id missing from the index is reported separately as `event=view_divergence_absent` (deliberately not matching a grep for `event=view_divergence task=`), and each pass ends with one `event=view_divergence_summary compared= divergent= index_age_seconds= warnings=`. `compared` counts joined ids, so an empty or failed index reads as `compared=0` rather than agreement. The check is advisory: a read failure is logged and the pass drives its candidates unchanged, no read happens before the vault-classification early returns or after the budget is spent, and it changes no eligibility, admission, capping or spawning. A deployment without a vault-api URL builds no client and emits nothing. The client is wired through `WithVaultAPIIndexClient`, so no existing `NewTaskEventHandler` call site changes. Outcomes are counted in a new `executor_view_divergence_total` counter labelled by a closed `result` set: `ok` and `read_error` increment once per pass that reaches the check, `mismatch` and `absent` once per task id, and all four series are pre-initialised at zero. It is a new name rather than a value on `executor_reconcile_passes_total` because `task_vault_mismatch` classifies vault ownership over the in-memory snapshot, not a per-id file comparison. Semantics are pinned in `docs/vault-api-task-index.md` § *Divergence check* and § *Metric contract*.

- feat: **the executor can read vault-api's whole task index in one bounded, authenticated call.** `VaultAPIIndexClient` (`pkg/claim/vault_api_index_client.go`) issues one unfiltered `GET /api/v1/tasks`, bounded at 32 MiB through `io.LimitReader`, and decodes a typed `TaskIndex` of `items[].id`/`status`/`phase` plus `total`, `warnings` and the server-computed `index_age_seconds`. It ships the client only; nothing consumes it yet. The auth header pair is extracted into `setVaultAPIAuthHeaders` so the claim and index clients cannot drift — `X-Gateway-Initator` stays misspelled because the server compares that exact name. `items` and `index_age_seconds` are required (a missing key is a `read_error`, never an empty index), `items: null` is a legitimate empty index, and `total`/`warnings` default to 0. The request carries no `cluster=` filter, because a filtered read omits files with no cluster frontmatter and manufactures `absent` divergences. The contract, including the unrecorded serving vault-api version, is pinned in `docs/vault-api-task-index.md`.

## v0.45.1

- fix: **a redrive-capped task is released by a 6 h window instead of staying capped forever.** The streak persisted as `claims/redrive/<task>/<phase>/<n>` refs was bounded by a `lease_until` nothing ever read: `RedriveStreakLeaseDuration` was documented as informational, `Count` counted every ref regardless of its lease, and the three release paths (`redriveStreakCapped` never clears on the cap, `recordRedriveSpawn` resets only after a successful spawn, `clearRedriveStreak` fires only on a terminal state) are each unreachable for a task that cannot spawn. The persistence was intended to survive restarts and does; the side effect was that a systemic outage — every task failing its three attempts at once — left the whole fleet stopped *after* the cause was fixed, recoverable only by an operator deleting refs by hand. The window is now 6 h and the read side honours it: `Count` skips refs whose `lease_until` has passed, `Snapshot` skips them too — load-bearing rather than tidy, because the reconcile pass answers every candidate's cap check from that one prefix snapshot, so filtering only `Count` would release the Kafka path and leave the re-drive path capped forever — and `Record` prunes the expired refs of its own task so a released streak restarts at 1 instead of continuing a dead sequence. Pruning is scoped to one task under the streak prefix, never a walk of `claims/redrive/`, because the reason store shares that ref space. The cap itself is unchanged: three live refs still refuse a fourth spawn, and an absent or unparseable `lease_until` counts as live so a malformed ref can never release a genuinely failing task. The in-memory floor expires on the same window, since the cap check takes `max(memory, stored)` and a permanent in-memory 3 would otherwise keep a task capped after the store had released it.

## v0.45.0

- feat: **a Config can declare itself the designated default for a task_type, so a type claimed by several CRs resolves instead of refusing.** `healthcheck` is claimed by 14 Configs on dev and 13 on prod, `llm` by 6 and 3; `ResolveByTaskType` matched every one of them, `narrowByAssignee` narrowed none, and the call returned `ErrConfigAmbiguous` for every record of those two types — 42 `in_progress` records sat in the store with an empty `assignee`, 8 of them `healthcheck`. `ConfigSpec.defaultForTaskTypes` is now part of the CRD schema, and the resolver reads it only after the assignee tier has failed: exactly one match declaring itself the default wins, zero or several leave the refusal untouched. That is an explicit declaration on the Config, not a guess, so none of the five contract tests inverts. `previous_assignee` is additionally passed on only when the Config it names actually declares the record's type — `claude-interactive` declares `llm`, so a `healthcheck` record escalated to it carried an input that could only ever produce the ambiguity it was meant to break.

## v0.44.0

- feat: **the spawn counter carries the namespace the Job landed in.** `agent_executor_jobs_spawned_total` was a label-free counter, so it could answer "how many Jobs spawned" and never "where" — which made it useless for the one question the sandbox migration turns on: whether a fleet stopped creating Jobs in its control namespace after moving them into per-domain sandboxes. Any spawn anywhere satisfied a read that was supposed to prove placement. It is now a `CounterVec` labelled `namespace`, carrying the **resolved** value from `ResolveJobNamespace`, not the Config's raw `jobNamespace`: empty means "the executor's own namespace", so labelling that `""` would leave a control-namespace spawn indistinguishable from a sandboxed one. A value that cannot be resolved is reported as `unresolved` rather than collapsed into the executor namespace, so a broken read is visible as itself instead of reading as a control-namespace spawn; that sentinel is the counter's only bounded value and the only series seeded at startup, since a `CounterVec` with no series registers no metric family at all and a counter absent until the first spawn is indistinguishable from one that was never wired up. Existing queries and dashboards are unaffected — a selector without the label matches every value.

- fix: **a `pod_crash_no_stdout` failure now arms the trigger cap, so the record reaches the operator inbox instead of accruing a counter nothing reads.** `PublishFailure` cleared `current_job`, bumped `trigger_count`, and did nothing else, while its interface doc comment claimed the retry cap in `result_writer.go` handled the rest. It does not, and never did: `applyTriggerCap` runs on the result-merge path only, and these writes take the atomic frontmatter-command path (`buildUpdateModifyFn`), which never reaches it. The escalation that does exist is the controller's increment executor, which clears `assignee` — the operator-inbox signal — once `trigger_count` reaches an **explicitly set** `max_triggers`; an absent key means no cap, so a record without one accrues the counter forever and is never surfaced. A crash before the first stdout write leaves nothing for the deliverer to act on, which is precisely the class nobody sets the key on by hand. The write is gated on `ParseZombieReason(reason) == ZombieReasonPodCrashNoStdout`, not string equality: the reason is a raw string shared by all eight classes, seven of which already carry their own escalation semantics, and a literal comparison would also miss the suffixed form (`pod_crash_no_stdout (Error/1)`). An already-present `max_triggers` is left untouched — the controller applies `Updates` blindly, and records at 5 and 6 exist, so halving a deliberate budget would be a regression rather than a repair. Order between the update and the increment is not guaranteed (nothing keys the two commands to one partition), so a reversed pair costs one failure cycle and never the escalation: the update is idempotent, and every later cycle finds the key present.

## v0.43.2

- refactor: **every lease is held through the typed vault-api claim client; git-rest now serves only the redrive counters.** `LeaseManager` spoke git-rest's vocabulary — a ref key, an expected SHA, a prefix listing, an absolute `lease_until` — none of which is a claim. It now acquires, renews, releases and lists through `ClaimClient`, which addresses a *target* (task, repository, or one pull request) with a holder and a TTL and returns a lease token. `targetFromKey`/`KeyFor` are the two halves of the one key format, mirroring vault-api's own inverse, so a claim a listing returns is addressable without re-deriving it from a task body. `Recover` lists by holder instead of enumerating `claims/` and filtering, which is also why the redrive-streak skip and the cluster filter are gone: the server excludes non-claim keys and narrows by holder itself. `ClaimRefClient` stays for `RedriveStreakStore` and `RedriveReasonStore`, whose refs are counters and not leases.
  ⚠️ **`Renew` now carries the holder, and that is a fix, not a rename.** The route writes the holder it is given, so the previous body — holder omitted — would have been refused `400 invalid_holder` on every renew and, had it been accepted, would have erased the holder a recovery listing filters on. A create also reads before it writes: the typed acquire takes over an expired lease by itself, which is right for a takeover and wrong for a create, so the create refuses an existing claim outright and only `Takeover` displaces one, after `TakeoverGrace`. The consequence is one fewer write on the takeover path, and it is what the updated expectations assert.
  ⚠️ **`VAULT_API_URL` and `VAULT_API_GATEWAY_SECRET` are read now, and a claim-taking mode without a URL fails closed at startup.** The chart has set both since `agent` v0.42.0; nothing read them. The lease manager has no fallback to the ref client — reads on one service and writes on another is exactly the split this change removes — so a nil client is a construction error, never a degraded mode.

## v0.43.1

- fix: **a record whose spawn count outran its published failures is classified again instead of being abandoned at the cap.** `classifyRedriveReasons` refused to classify whenever `len(reasons) < count`, on the assumption that every spawn produces exactly one reason. It does not: `recordRedriveSpawn` increments the streak on every successful spawn on every path, while a reason is recorded only from `PublishFailure`, so a spawn that publishes no failure — a reconcile re-drive whose job vanished, exactly what `event=reconcile_redrive` is — advances the streak without adding a reason. Once the two drifted by one the record was stranded permanently: classed `unknown` it earned no transient extension and triggered no abort, so its spawn was refused, and a record that cannot spawn can never earn the missing reason, so the gap never closed. Observed live on dev 2026-10-26: `task=A0118D66-…` reached the cap **under `v0.40.0`** carrying `deadline_exceeded,deadline_exceeded,pod_crash_no_stdout` at `streak=4 cap=3` and read `class=unknown`. The window is now the most recent `min(count, len(reasons))` reasons, so the streak only bounds how far back to look. `broken` still requires the cap's worth of identical broken signatures — fewer is partial evidence and must not close a record — and everything else is transient, which earns the bounded extension and ends the record either way, so nothing is left abandoned at the cap. No reasons at all, or all literal `unknown`, still classifies `unknown` and closes nothing, so the pre-`v0.40.0` residue is untouched. `docs/claim-lease-protocol.md` § *The cap's decision* is updated in the same change, since all three of its class definitions described the old equality and would otherwise have contradicted the code.

## v0.43.0

- fix: **a task whose status is terminal is no longer a candidate, whatever its Config's `trigger.statuses` says.** `reconcileTask` and `parseAndFilter` each gated status on the per-Config allow-list alone, so a Config that listed `completed` or `aborted` admitted finished tasks — and the candidate set is what the re-drive cap is charged against, so a terminal task admitted there is capped on every pass forever: `clearRedriveStreak` fires on a terminal *transition*, and for a task that went terminal before this executor saw it that transition never comes. `IsTerminalStatus` is now the status-side twin of `IsTerminal`/`terminalPhases` and is applied unconditionally in both filters, ahead of the allow-list, mirroring the terminal-phase rule that was already in place: a Config may narrow eligibility, never widen it past "the work is over". `cleanupTerminalTask` reads the same set instead of repeating the two literals. The skip is reported as `executor_task_events_total{result="skipped_terminal_status"}` rather than folded into `skipped_status` — both refuse the task, only this one says why.
  ⚠️ **This reverses the behaviour asserted by the spec `spawns job when Config has Trigger.Statuses=[completed] and event status=completed`**, which is updated in the same change; it encoded the allow-list-is-authoritative reading and not a used configuration — all 33 Configs across dev and prod declare `statuses: [in_progress]` and no other value, so nothing in the fleet changes today. The rule closes the class rather than a live instance.

## v0.42.0

- feat: **Give the typed claim client the two capabilities `LeaseManager` needs before it can be rewired onto it: enumeration, and a per-PR target.** This is the preparation half of the rewire, not the rewire itself — nothing calls `ClaimClient` yet, which is exactly why it can be extended safely now.
  **`List(ctx, holder)`** is new. `ClaimClient` was Acquire / Renew / Release / Read only, and a key-at-a-time read cannot answer the question a restarting executor asks: *which claims do I already hold?* `Recover` must enumerate before it can re-adopt, fence or release anything, so the client gains the operation that `GET /api/v1/claims` serves. `holder` empty lists everything; the narrowing is a convenience, not an access boundary — that is the gateway secret's job.
  **`Claim.TaskID`** is decoded from the response, because it is what makes a listed claim groupable: a repository claim belongs to no task of its own, so recovery pairs a repository claim with its per-PR claim **by task id** rather than by key shape.
  **`NewPRClaim(owner, repo, number)`** addresses one pull request, and `ClaimTarget.path()` now serves `/api/v1/repos/{owner}/{repo}/pulls/{number}/claim`. A number without a repository is deliberately **not addressable** — the route has no shape for it, and inventing one would claim a key the server never serves, so the caller would read the resulting 404 as "somebody else holds it".
  ⚠️ **`Acquire` and `Renew` take a `claimantTaskID`, and this is the part a naive rewire would have broken on.** The transport stores a task id on every ref, and vault-api answers `400 missing_task_id` for a repository or per-PR write that carries none — so pointing `LeaseManager` at the client without plumbing this would make every repository claim fail at its first write. For a task claim the argument must stay empty: the server derives the task id from the address, and sending one would let a run claim under a task it did not address. **Both halves are now enforced in the client**, not merely documented: a repository or per-PR claim without the id, and a task claim carrying one, are refused locally with `ErrClaimTargetInvalid`. The task-claim half is the one the server cannot catch — it derives the id from the address, so a supplied one is either ignored or, worse, accepted.
  ⚠️ **A target that sets two addressing forms is refused, and `Number` had to be added to that guard.** `isRepo()` is false for a target carrying only a `Number`, so `ClaimTarget{TaskID: "t-1", Number: "7"}` slipped past the existing TaskID-plus-repository check and matched the task branch — silently claiming a task the caller never named, which is precisely what the type's own contract forbids. A pull-request number is also now required to be digits: `url.PathEscape` does not escape `.`, so a number of `..` would survive as `/pulls/../claim` and a server that cleans paths could resolve it to the repository route.
  `decodeClaim` was split so the single-claim routes and the listing share one validator (`claimFromResponse`), so a listing item cannot silently default a missing lease or token and hand back a claim that can be neither renewed nor trusted.

## v0.41.0

- fix: **join the repository and pull-request claim keys with `/` instead of `-`, because the hyphen join let two repositories share one lock.** A claim key has to identify exactly one object, and it did not: `DeriveClaimKey` built `claims/repo/<owner>-<repo>` and `DeriveClaimKeysWithBody` built `claims/pr/<owner>-<repo>-<number>`, while a hyphen is legal inside both components (the validator accepts `[A-Za-z0-9._-]`). So `owner=a-b, repo=c` and `owner=a, repo=b-c` both derived `claims/repo/a-b-c` — two distinct repositories aliasing one lock, which means the mutual exclusion silently did nothing and two runs could proceed against the same repository each believing it held it. The PR form was worse still, since the number is appended with the same separator. The join is now `/`, which cannot collide because `/` is rejected inside a component, and it matches the streak keys (`claims/redrive/<taskid>/<phase>/<n>`) that were already slash-separated. ⚠️ **This is a wire-format change and must be deployed in lockstep with `vault-api`, which reproduces this derivation rather than deriving its own** — a period where one side writes `claims/repo/a/b` and the other reads `claims/repo/a-b` is a period where the lock excludes nothing. In-flight claims carry a 5-minute lease, so a rolling deploy orphans each one for at most one lease and the next acquire takes it over rather than refusing: vault-api's `acquireToken` reads the existing ref and, when the lease has expired, returns **that ref's own SHA** as the compare-and-swap token with no live holder, so the acquire succeeds instead of answering `409 claim_held`.

## v0.40.0

- fix: **the consecutive-re-drive cap now closes a broken record instead of abandoning it, and extends a transient one.** Reaching `maxConsecutiveRedrives` used to refuse the fourth spawn forever while leaving the record `in_progress` with no reason recorded — the task stopped burning Jobs but nothing said why, and nothing ever closed it. Each attempt's failure reason is now persisted next to the streak as `claims/redrive-reason/<taskid>/<phase>/<reason>/<n>`, numbered chronologically across every reason, and the cap classifies the record when it reaches the threshold. Three identical broken signatures (`pod_crash_no_stdout`, `pod_oom_killed`, `type_mismatch`) close it with `status: aborted` and `aborted_reason: capped:broken-signature`; a transient failure (`image_pull_backoff`, `deadline_exceeded`, `pod_evicted`, `pod_not_scheduled`, `executor_watch_lost`) earns a bounded extension of `transientRedriveBudget` (3) spawns and is then closed with `capped:transient-retries-exhausted`; no reasons, a short count or all-`unknown` refuses the spawn and closes nothing, because closing on unread history is not the safe direction. The close-out write also sets `gate_successor: "none"` and clears `current_job` — the pair vault-cli requires before it accepts `aborted` — and is deduped per task and skipped when the task is already aborted. The classifier now runs on the ordinary path: the in-memory short-circuit and the reconcile pre-check that made it reachable only after a restart are gone, so a task this process itself counted to the cap is classified too. `event=redrive_capped` gains `class=` and `reasons=`, and the new `executor_redrive_aborted_total{reason}` is pre-initialised for its closed two-value vocabulary (unlike its unbounded neighbour `executor_redrive_capped_total`, whose omission is deliberate). Reason refs carry the existing `redrive-streak` cluster sentinel, so an older binary's recovery skips them, and they are cleared on the terminal path and at a streak's first spawn so they always describe the current streak. The formatted `pod_oom_killed (OOMKilled/137)` reason is normalised to its vocabulary value before it is stored; its spaces and parentheses are not valid key segments.
- feat: **add a typed claim client for the vault API, alongside the existing git-rest one.** `ClaimClient` speaks the claim's own vocabulary — `Acquire(target, holder, ttl)` returns a `lease_token`, then `Renew`, `Release`, `Read` — addressed by a `ClaimTarget` that is **either a task identifier or a repository**, so no caller spells a ref key, an expected SHA or a prefix. The existing `ClaimRefClient` is deliberately kept: `RedriveStreakStore` uses the same git-rest refs as a **counter** (`Count`/`Record`/`Clear` over `claims/redrive/<taskid>/<phase>/<n>`), which is not a lease and has no typed home yet, so deleting it would break that consumer for no criterion gain. The errors are separate because the remedies are: `ErrClaimHeld` is a `*ClaimHeldError` carrying the holder and `lease_until` so a caller can report who blocked it, `ErrClaimFree` is `Read` on an idle target, `ErrLeaseLost` is a stale token on renew or release (re-acquire, never retry), and `ErrClaimTargetInvalid` is refused **locally** by all four methods — an empty path segment would come back as a 404 that reads like a missing task. (The review caught that `Renew` did not actually honour this: it built its path as `path()+"/renew"`, which for an unaddressable target is the non-empty `"/renew"`, so the guard never fired. Fixed, and covered by a spec case that asserts no request is issued.) **The second review round found a blocking defect the first could not see, and neither could the tests:** the request helper returned `*http.Response` to a caller that read the body *after* the helper's deferred `cancel()` had fired — and per `net/http` the request context governs the response body's lifetime, so every decode would have failed with `context.Canceled` in production. `httptest` buffers small bodies before `Do` returns, so no unit test could reproduce it. The helper now reads the body **inside** the context's lifetime and returns bytes, capped at 10 MiB (matching `ref_client.go`), so an oversized or HTML error page is detected rather than streamed into memory. Also from that round: `lease_until` and `lease_token` are now **required** in a response rather than silently defaulted, an unparsable held-claim timestamp fails instead of yielding a zero lease that reads as "already expired", an **ambiguous** target that sets both a task and a repository is refused locally instead of silently preferring the task, unexpected statuses return a typed `*StatusError` carrying the code and a `Retryable()` predicate, and the constructors follow the `New*` convention. Two contract details are asserted by the spec because both were learned by measurement: the release token travels in the JSON **body** (a header answers `400 invalid_body`), and a response body is never echoed into an error, since it can carry a holder or a token. **Not yet wired:** `LeaseManager` still runs on the git-rest client; this is the seam only, so the repo is never left half-migrated.
